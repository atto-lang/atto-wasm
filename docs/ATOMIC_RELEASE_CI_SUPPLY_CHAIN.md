# Atomic Wasm release: CI dependency and promotion audit

## Reproducible TypeSpec installation

The native contract workflow uses the checked-in npm v3 lockfile with exact direct
dependencies `@typespec/compiler@1.17.0` and `@typespec/json-schema@1.17.0`.
Run `npm ci --ignore-scripts --no-fund --no-audit` rather than `npm install`
to enforce that dependency resolution matches `package-lock.json`. CI also
executes `npm audit --audit-level=moderate` as a fail-closed advisory gate,
and verifies the actual emitted schemas against the normative JSON Schema.

The lockfile was generated by a funded ubuntu-24.04 GitHub Actions runner from
this source package manifest, then the same runner completed `npm ci`.
The resulting dependency graph had 64 package records, 63 integrity-pinned
downloaded packages, and **zero npm audit vulnerabilities at generation time**.

The older pinned 1.4.0 toolchain reported six package advisories (five high,
one moderate). They were associated with the TypeSpec compiler and its
transitive globby / fast-glob / micromatch / braces / ajv dependencies.
Those findings do not on their own prove Wasm guest runtime exploitation.
The new tree must continue to pass the emitted-schema 85-case differential
gate and genuine source compiler integration.

## Remaining supply-chain scope

- npm advisories depend on registry state; the gate is rerun and may fail if
  new advisories are published.
- The Python `jsonschema` direct version, `clang`/OS packages, and GitHub
  Actions action references are not yet cryptographically pinned end-to-end.
  The npm lockfile is **not** an attestation for those tools.
- The emitted-schema run exercises a bounded corpus, not arbitrary JSON.
  Normative JSON Schema and runtime admission checks remain necessary.

## Promotion prerequisites

The funded test mirror is acceptable as technical evidence only when the
complete source Git tree SHA matches the source branch and GitHub's proposed
final merge tree. Merely matching a commit message or selected files is
insufficient.

Before merging, require an independent approval (a reviewer other than the
PR author) and an administrator-enforced branch rule with the four workflows:
`wasm`, `llvm-atomic`, `atomic-contracts`, `tlc-artifact-publication`.
If the originating organization cannot allocate GitHub Actions runners,
resolve that admission issue or explicitly approve an equivalent independent
SHA-bound release gate. This documentation **does not enable** GitHub branch
protection. Never merge to work around review/check requirements.

After merge, verify the actual `main` tree and rerun/record post-merge
evidence before promoting a release. Atomic mode remains opt-in, automated
GC remains disabled, and process-kill testing is not a hardware power-loss
durability guarantee.

See GitHub issues #23 (governance), #25 (dependency audit), and
`ores-truffle-oreslang/oreslang-platform-conformance` issue #19.


## Hash-locked Python verifier

`contracts/python-requirements.lock` pins the Python Draft 2020-12 JSON
Schema validator and its transitive dependencies by exact versions plus
download SHA-256 hashes. The lock was compiled and successfully installed in
a funded Ubuntu 24.04 runner with a Python 3.12 environment. Contracts CI
uses the immutable `actions/setup-python` v5.6.0 Git commit for CPython
3.12.15, provisions an isolated virtual environment, and runs
`pip install --require-hashes`. No unpinned Python dependency resolution is
allowed in this verification job. The lock carries hashes for several
platform distributions; a new target platform must be independently tested.

## Native toolchain observations

The native LLVM workflow SHA-pins its own Oreslang compiler source blobs and
now writes `build/native-toolchain-attestation.json`, recording the source
commit and tree, built compiler SHA-256, installed Ubuntu package versions,
resolved Clang/CMake executable SHA-256 and versions, and the two verified
sealed Wasm output identities. The CI workflow uploads this evidence as
`native-wasm-toolchain-attestation` for 30 days.

The attestation is deliberately labelled an **observation**, not a signed
provenance, deterministic-build proof, or guarantee against a compromised
runner. The LLVM/Clang packages are installed from live Ubuntu repositories
and their exact versions are *recorded* rather than hard pinned. Fully
reproducible native builds still require a digest-pinned OCI image or fixed
package repository snapshot and independent rebuild comparisons.

## Durability fault coverage

The Node tests inject exceptions at three ordered boundaries: immediately
after release-directory rename but before release-root `fsync`, after
temporary-pointer `fsync` but before pointer rename, and after pointer
rename but before pointer-parent `fsync`. The first two may leave
independently verified unreferenced release directories but **must not**
advance the selected pointer. The last is an uncertain outcome that carries
the attempted release identity, cannot be translated into ordinary abort,
and must be reconciled by a verified read.

These deterministic injections exercise API state/error invariants only.
They **do not** simulate a real block device cache, an unclean VM reset, or
hardware power loss. Physical fault/recovery qualification remains a separate
mandatory release-hardening milestone.
